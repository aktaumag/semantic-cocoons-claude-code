# Система семантического кокона

## Ментальная модель

Кокон — самостоятельный тематический кластер. Он охватывает главный пользовательский домен через связанные сущности и намерения, а не через россыпь похожих ключей. Внутри кластера архитектура одновременно объясняет тему пользователю, поисковому роботу и редакционной команде.

Термины ниже — удобная проектная модель, а не названия подтвержденных текущих алгоритмов Google:

- **Сущность:** объект, процесс, характеристика, проблема или стандарт, вокруг которого строится полезный ответ.
- **Salient Terms:** отличительные атрибуты, без которых сущность нельзя содержательно объяснить. Они не равны набору LSI/синонимов.
- **Topic embedding / семантическая близость:** рабочая проверка того, объяснима ли ссылка, соседство и структура человеку с точки зрения общего контекста.
- **LinkValue:** условное имя для ценности внутренней ссылки. Не рассчитывай числовые коэффициенты и не заявляй, что Google использует это как публичный фактор.

## Режим «максимально полезное покрытие»

Используй этот режим для старта с нуля: пользователю достаточно написать «Спроектируй максимально полезное покрытие для: ремонт холодильников». Сайт, готовые URL, семантическое ядро или JSON не обязательны. При наличии страны, языка, бизнес-модели, услуг, опыта экспертов, каталога или данных о клиентах используй их; при отсутствии — проектируй концептуальную карту и отмечай допущения, а не подменяй их «данными рынка».

### Что должно получиться

Сначала отдай шесть результатов:

1. **Границы темы:** что включено, что исключено и почему.
2. **Семантическая вселенная:** кандидаты по классам — объекты/типы, части и параметры, процессы, неисправности, сценарии, коммерческие задачи, доверительные/нормативные вопросы, а для локального спроса — география.
3. **Реестр коконов:** самостоятельные кластеры, их Target-тема, бизнес-задача и причина независимости.
4. **Карта каждого кокона:** Target → Mixed → Support с доминирующим интентом, сущностью, JTBD, родителем и причиной уникальности каждой страницы.
5. **Стоп-лист:** что объединить, оставить H2/FAQ в существующей странице или исключить как нерелевантное/слабое.
6. **Порядок запуска:** сначала коммерчески значимые Target/Mixed и уже существующие сильные материалы, потом самые полезные Support, затем расширения по подтвержденным пробелам.

Это «максимум полезного покрытия», а не максимум URL. Не генерируй контент, JSON, вымышленные URL или сотни тем, пока пользователь не просит следующий этап.

### Алгоритм классификации

Для каждого кандидата выполни проверку по порядку:

1. Имеет ли он самостоятельную сущность и пользовательскую задачу?
2. Отличается ли его доминирующий интент от уже принятой страницы?
3. Можно ли дать уникальный и достоверный ответ/услугу, а не вариацию одного текста?
4. Есть ли для него естественный родитель и контекстные соседние страницы?
5. Есть ли причина для отдельного Target-кокона: отдельное предложение или аудитория, самостоятельная широкая тема, минимум 4–6 осмысленных подкластеров и возможность наполнить их уникальными Support-материалами?

Классифицируй результат так:

| Вердикт | Когда применять | Следствие |
| --- | --- | --- |
| Новый кокон | Все пять проверок пройдены | Создай отдельный Target с собственной трехуровневой картой; связь с другими коконами — только Target → Target/bridge |
| Mixed | Это крупный подкластер того же Target, но не самостоятельный бизнес-домен | Под ним собери свои Support-страницы |
| Support | Один узкий вопрос, ошибка, процедура, параметр или long-tail задача | Один родитель Mixed, Mother-ссылка вверх |
| Блок/FAQ | Нет отдельного интента или самостоятельного материала | Оставь частью наиболее подходящей страницы |
| Исключить | Нет предметной связи, спроса/ценности или это ассоциативный дрейф | Не добавляй в карту |

### Стоп-правила и «не бесконечность»

Не делай «кокон внутри кокона» как очередной уровень URL. У самостоятельного кокона всегда максимум три роли — Target, Mixed, Support. Если Mixed-подтема стала настолько широкой, что проходит критерии нового кокона, вынеси ее горизонтально в самостоятельный кокон с собственным Target, а не углубляй старую ветку до уровня 4/5/6.

Останавливай расширение, если хотя бы одно условие верно:

- новая страница перехватывает тот же интент, что существующая;
- она не дает уникальных фактов, процедуры, выбора, услуги или решения;
- ее нельзя объяснить пользователю естественным путем от родительской страницы;
- тема не относится к бизнесу или у команды нет права/экспертизы для достоверного ответа;
- проверка SERP, GSC, продаж или интервью не подтверждает отдельную задачу;
- это лишь словоформа, город, бренд или характеристика без самостоятельного содержания.

Если доступны поиск, GSC, CRM или интервью, они служат проверкой границ и приоритетов. Без них не заявляй «максимальный спрос» или «полное покрытие рынка»: назови карту первой гипотезой и перечисли, какие данные подтвердят ее.

### Короткие запросы

Вызови skill синтаксисом своего клиента, а затем передай один из этих запросов. В Codex это обычно `$semantic-cocoons`, в Claude Code plugin — `/semantic-cocoons:semantic-cocoons`.

```text
Спроектируй максимально полезное покрытие для: ремонт холодильников.
```

```text
Спроектируй максимально полезное покрытие для: ремонт холодильников. Рынок: Москва, Россия. Бизнес: аварийный сервис коммерческого холодильного оборудования. Цель: заявки. Сначала только карта возможностей и реестр коконов.
```

Не нужно добавлять «раздели интенты», «найди родителей», «остановись при дублях» или «отдели коконы от веток»: это уже обязательная логика режима. Проси JSON отдельно только после утверждения карты: «Преобразуй утвержденную карту в JSON для CMS».

## 1. Разведка

Начинай с данных в порядке надежности: собственные GSC и аналитика, ассортимент/документация/эксперт, SERP и конкуренты, затем гипотезы LLM. Для каждого кандидата зафиксируй:

| Поле | Смысл |
| --- | --- |
| Entity | Каноническое название сущности |
| Salient Terms | Не менее пяти идентифицирующих признаков, когда они действительно известны |
| Context terms | Смежная терминология, сценарии и словарь пользователя |
| Intent | Информационный, коммерческий, навигационный или сравнительный; один доминирующий на страницу |
| JTBD | Какую задачу и на какой стадии решает пользователь |
| Evidence | Откуда вывод: GSC, SERP, каталог, документация, интервью, эксперт |
| Confidence | Подтверждено / вероятно / гипотеза |

Не придумывай MID. Если машиночитаемый контракт требует поле для него, используй `null` либо явный placeholder `/m/XXXXX`, но не выдавай его за реальный идентификатор.

Проверки до архитектуры:

- раздели омонимы и разные предметы под одинаковыми словами;
- объедини вариации, отвечающие на один и тот же интент одной страницей;
- отдели сервисную/коммерческую задачу от образовательной, если SERP и ожидания пользователя расходятся;
- не путай общую смежность с достаточной близостью для одной ветки;
- запиши, какая существующая страница уже претендует на тот же запрос.

## 2. Архитектура

### Уровни

| Уровень | Роль | Назначение | Типичный контент | Обязательные отношения |
| --- | --- | --- | --- | --- |
| 1 | Target / Матриарх | Одна главная страница темы | Целостный навигационный или коммерческий/экспертный обзор | Вниз на все Mixed; входящие Mother от Mixed |
| 2 | Mixed / узел | Под-кластер, уточняющий намерение | Выбор, классификация, сравнение, обзор метода | Вверх Mother на Target; вниз Daughter на свои Support |
| 3 | Support / поддержка | Один узкий long-tail вопрос или задача | Инструкция, FAQ, диагностика, конкретная характеристика | Вверх Mother на свой Mixed; Sister только внутри своей ветки |

План по умолчанию — одна Target, 4–6 Mixed и 5–15 Support на Mixed. Это ориентир для достаточно широкой темы, не обязательная норма. На маленьком сайте, локальном сервисе или при скудных данных уменьши масштаб; новая страница должна иметь уникальный интент, материал и бизнес-смысл.

### URL и карта страниц

Предпочитай ясную стабильную иерархию, например `/hub/mixed/support/`, когда она согласуется с существующей информационной архитектурой. Не мигрируй URL только ради модели кокона: оцени редиректы, каноникалы, исторический трафик и цену изменений.

У каждой страницы должны быть: URL, уровень, synopsis, фокусная сущность, доминирующий интент, JTBD, родитель, ключевые доказательства/источники, Salient Terms, статус (существует/обновить/создать) и причина, почему она не каннибализирует соседнюю страницу.

## 3. Матриархальная перелинковка

Типы связей:

| Тип | Направление | Задача | Допустимость |
| --- | --- | --- | --- |
| Mother | Support → Mixed; Mixed → Target | Консолидация и путь назад к более общему ответу | Обязательна |
| Daughter | Target → Mixed; Mixed → Support | Навигация и объяснение вложенности | Нужна, где дочерняя страница полезна |
| Sister | Support ↔ Support одной ветки Mixed | Переход между тесно связанными микро-задачами | Обычно до двух релевантных исходящих; не обязательна |
| Niece / межкоконовая | Target → Target другого кокона | Логичный следующий шаг | Исключение, лучше согласованный bridge/hub; не ставить по умолчанию |

Инварианты:

1. У каждого Support ровно один родительский Mixed и хотя бы одна уместная Mother-ссылка на него.
2. Support не ссылается прямо на Target и не уходит в Support другого кокона.
3. Mixed не оставляют без дочерних страниц, если он заявлен как узел; если поддержки не нужны, сожми его в Target или самостоятельную страницу.
4. Target не перегружай ссылками на листья: она ведет к Mixed, а не дублирует навигацию всего раздела.
5. Сестринские ссылки разрешай по общим сущностям и реальной последовательности задачи, не «для плотности».
6. Межкоконная ссылка — только явное, полезное продолжение. При неуверенности не ставь ее.

Ориентиры плотности из методики: Target обычно 10–15 внутренних связей, Mixed 8–15, Support 3–5 (одна Mother и до двух Sister). Это не KPI: навигация и контент могут требовать меньшего или большего числа. Не ухудшай читабельность ради лимита.

Для каждой ссылки зафиксируй `source_url`, `target_url`, `type`, `priority`, `anchor_text`, `required_terms_in_context`, `context_placement`, `why_relevant`. Анкор естественно называет сущность цели; окружающий текст обычно включает 2–3 признака/термина целевой сущности. Не обещай коммерческий результат от нейтральных справочных ссылок и не переспамливай анкор.

## 4. Контентное производство

Пиши после утверждения карты и ссылок. Сохраняй одну утвержденную роль каждой страницы; не добавляй новые URL или связи тихо во время написания.

| Роль | Контентная работа | Практический ориентир из книги |
| --- | --- | --- |
| Support | Прямой ответ на микро-интент; проблема → решение → результат; технические детали; FAQ по необходимости | 600–900 слов, без воды; длина не заменяет факты |
| Mixed | Синтез дочерних тем, сравнения, условия выбора, таблица параметров, экспертный вывод | 1 200–1 800 слов |
| Target | Главная ценность темы, выводы из Mixed без повторов, навигация, доверительные сигналы, схема темы | 2 500–4 000 слов |

Применяй длины как диапазоны планирования, не как требование. Для каждого текста:

- давай проверяемый **information gain**: процедуры, условия, параметры, ограничения, оригинальные наблюдения, фото/данные/кейсы, если они достоверны;
- не имитируй опыт, тестирование, сертификаты или авторство;
- включай нужные Salient Terms естественно и лишь если они истинны для темы;
- встраивай только одобренные outgoing links c закрепленным контекстом;
- создавай логичную H1–H3 структуру и метаданные под реальный интент;
- при уместности предлагай Schema.org тип по содержанию (например, `FAQPage`, `TechArticle`, `Article`), с `about`, `mentions`, автором и организацией только на подтвержденных данных.

## 5. Валидация и рефакторинг

Аудитируй сначала карту, затем техническую реализацию, затем результаты. Найденные ошибки исправляй в версии карты; не исправляй молча контентом то, что является архитектурной проблемой.

### Архитектурный линтер

- Ровно одна Target, соответствующая стартовому URL.
- Нет страницы без логичного родителя; нет лишнего уровня/URL вне ветки.
- Нет сущности и интента, раздвоенных между несвязанными страницами.
- Нет Support с намерением или объемом Target, нет слишком широкой Support.
- Нет нерелевантных сущностей и «ассоциативного» дрейфа.
- Все ссылки существуют, указывают на конечный канонический URL, допустимы по направлению, имеют контекст и не выходят из кокона без причины.
- Нет сирот, редиректных цепочек, 4xx/5xx, noindex/robots-блокировки или противоречивых canonical в планируемом пути.

### После публикации

Проверь GSC, аналитику и логи, когда доступны: индексацию, каноникализацию, кластеры запросов, CTR и страницы входа, переходы внутри ветки, позиции по группам и конверсии. Под «здоровым коконом» понимай не одновременный рост всех URL, а подтвержденное улучшение покрытия пользовательских задач и бизнес-метрик. Анализируй изменения по периоду, устройству, региону и типу интента.

Расширяй только после аудита: найди неохваченную соседнюю сущность, докажи отдельный интент, добавь Support в правильную ветку, настрой Mother/Daughter, затем повторно проверь каннибализацию.

## Машиночитаемый контракт

Применяй эту структуру, когда пользователь просит JSON или нужен импорт в CMS/таблицу. Перед выводом проверь JSON. Можно добавлять поля с доказательствами и статусами, но не меняй URL/страницы при последующей генерации контента без явного согласования.

```json
{
  "cocoon": {
    "topic": "string",
    "start_page": "https://example.com/topic/",
    "language": "ru",
    "pages": [
      {
        "page_level": 1,
        "page_role": "Target",
        "page_url": "https://example.com/topic/",
        "page_synopsis": "string",
        "dominant_intent": "commercial | informational | comparative | navigational",
        "entities": [
          {
            "entity_name": "string",
            "knowledge_graph_mid": null,
            "salient_terms": ["string"],
            "search_intents": {"informational": "string", "commercial": "string", "navigational": "string"}
          }
        ],
        "outgoing_links": [
          {
            "link_type": "Mother | Daughter | Sister | Niece",
            "target_url": "string",
            "target_page_level": 2,
            "anchor_text": "string",
            "required_terms_in_surrounding_text": ["string"],
            "context_placement": "string",
            "priority": "High | Medium | Low",
            "why_relevant": "string"
          }
        ]
      }
    ]
  }
}
```
